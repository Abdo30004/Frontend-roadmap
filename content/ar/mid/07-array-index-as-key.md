# ما الذي يتعطل فعلياً عند استخدام فهرس المصفوفة كـ Key في React؟

**Level:** Mid
**Merged from (original phrasings):**
- ما الذي يتعطل ويحدث فعلياً عند استخدام الـ index كـ key في مصفوفات React؟

## The concept
- يستخدم React خاصية الـ `key` لمطابقة العناصر بين دورات التصيير: "المكون الذي كان يحمل المفتاح X سابقاً هو نفس المكون صاحب المفتاح X الآن". وبناءً على ذلك، يحتفظ React **بحالة هذا المكون (State)، وعقدة الـ DOM الخاصة به، ومراجعه (Refs)**، ويكتفي بتحديث الخصائص (Props).
- عند كتابة `key={index}`، يرتبط المفتاح **بالموقع والترتيب**، وليس **بالعنصر وبياناته**. فعند إضافة عنصر في البداية، أو الحذف من المنتصف، أو الترتيب، أو الفرز، يتغير العنصر الموجود في الفهرس 2 مثلاً، ولكن React يفترض: "المفتاح 2 لا يزال نفس المكون دون تغيير".
- ما الذي يتعطل فعلياً:
  - **الحالة المحلية ترتبط بالصف الخطأ**: حالة مربعات الاختيار (`checked`)، وحالة فتح وإغلاق العناصر المنسدلة، ووضع التعديل.
  - **المدخلات غير الموجهة (Uncontrolled inputs) تحتفظ بالنص القديم**: تتم إعادة استخدام عنصر `<input>` في الـ DOM، فيبقى النص المكتوب في نفس الموقع بينما تتحرك العناوين والبيانات للأعلى أو للأسفل.
  - **التركيز (Focus)، وموضع التمرير، والرسوم المتحركة، وعناصر الميديا** (مثل فيديو قيد التشغيل) تظل ملتصقة بالموضع الفهرسي لا بالعنصر الحقيقي.
  - **تدهور الأداء (Performance)**: الإضافة في مقدمة المصفوفة تغير خصائص كل الصفوف التالية، مما يفرض إعادة تصيير القائمة كاملة بدلاً من إضافة عنصر واحد فقط.
- استخدام الـ Index كـ Key مقبول فقط إذا كانت القائمة **ثابتة تماماً (Static)**: لا يُعاد ترتيبها، ولا تُفرز، ولا يُضاف إليها عناصر (إلا في النهاية فقط)، ولا تحتوي عناصرها على حالة داخلية (State).
- الحل الصحيح: استخدام **معرّف فريد وثابت مستمد من البيانات (Stable unique ID)** (مثل ID قاعدة البيانات أو الـ slug). وإذا قمت بإنشاء العنصر محلياً، فأنشئ المعرف لحظة **إنشاء العنصر** (`crypto.randomUUID()`)، وإياك أن تولده أثناء التصيير داخل الـ JSX.

## Real-life example
أداة لإدارة المهام تحتوي على قائمة مهام فرعية لكل مشروع. يحتوي كل صف على حقل نصي للملاحظات غير موجه (Uncontrolled) وحالة محلية لمربع اكتمال المهمة (`done`). تُضاف المهام الجديدة دائماً في **المقدمة**. حدد المستخدم مهمة "طلب المواد" كمكتملة وكتب في ملاحظتها "الاتصال بالمورد"، ثم أضاف مهمة جديدة في الأعلى بعنوان "حجز القاعة". فجأة، ظهرت "حجز القاعة" كمكتملة وتحمل ملاحظة "الاتصال بالمورد"، بينما أصبحت "طلب المواد" غير مكتملة وبملاحظة فارغة! حفظ المستخدم التغييرات فأرسل النظام الملاحظات الخاطئة تماماً للخادم.

```jsx
function TodoRow({ todo }) {
  const [done, setDone] = useState(false); // حالة محلية لكل صف
  return (
    <li>
      <input type="checkbox" checked={done} onChange={() => setDone(!done)} />
      <span>{todo.title}</span>
      <input name={`note-${todo.id}`} placeholder="Note" /> {/* غير موجه uncontrolled */}
    </li>
  );
}

function TodoList() {
  const [todos, setTodos] = useState([{ id: 'a1', title: 'Order materials' }]);

  const addTodo = (title) =>
    setTodos((prev) => [{ id: crypto.randomUUID(), title }, ...prev]); // إضافة في المقدمة

  return (
    <ul>
      {todos.map((todo, index) => (
        <TodoRow key={index} todo={todo} /> // خطأ: الـ key هو موقع الفهرس
      ))}
    </ul>
  );
}
```
ما شاهده React بعد إضافة "حجز القاعة" في البداية:
```
قبل الإضافة: key 0 -> "طلب المواد" (done=true, note="الاتصال بالمورد")
بعد الإضافة: key 0 -> "حجز القاعة"  -> أعيد استخدام نفس المكون: بقيت done=true واحتفظ بالملاحظة!
             key 1 -> "طلب المواد"  -> مكون جديد تم تركيبه: done=false وملاحظة فارغة تماماً
```

## How to fix it
```jsx
function TodoRow({ todo, onToggle }) {
  return (
    <li>
      <input type="checkbox" checked={todo.done} onChange={onToggle} />
      <span>{todo.title}</span>
      <input name={`note-${todo.id}`} placeholder="Note" />
    </li>
  );
}

function TodoList() {
  const [todos, setTodos] = useState([{ id: 'a1', title: 'Order materials', done: false }]);

  const addTodo = (title) =>
    setTodos((prev) => [{ id: crypto.randomUUID(), title, done: false }, ...prev]); // إنشاء الـ ID مرة واحدة

  const toggle = (id) =>
    setTodos((prev) => prev.map((t) => (t.id === id ? { ...t, done: !t.done } : t)));

  return (
    <ul>
      {todos.map((todo) => (
        <TodoRow key={todo.id} todo={todo} onToggle={() => toggle(todo.id)} />
      ))}
    </ul>
  );
}
```
سبب نجاح الحل: أصبح المفتاح (Key) ينتمي لهوية العنصر نفسه. وعند إضافة عنصر جديد في البداية، يتعرف React على مفتاح جديد واحد فقط ويصيّر له صفاً جديداً. وتحتفظ كافة الصفوف السابقة بعقد الـ DOM الخاصة بها ونصوص مدخلاتها وحالتها دون أي اختلاط. كما أن رفع حالة `done` لتكون جزءاً من كائن المهمة (Lifting state up) يضمن بقاءها عند الفرز أو الحفظ.

حلول خاطئة شائعة يجب تجنبها:
- `key={Math.random()}` أو `key={crypto.randomUUID()}` داخل دالة التصيير: ينتج عن ذلك مفتاح جديد تماماً مع كل تصيير، فيلغي React تركيب المكون ويعيد تركيبه بالكامل، مما يفقد المستخدم التركيز (Focus) والنصوص المكتوبة مع كل ضربة زر!
- `key={todo.title}`: العناوين ليست فريدة، وتكرارها يسبب تحذيرات واختلاطاً كارثياً في الصفوف.

### حيلة مفيدة: استخدام الـ Key عمداً لإعادة ضبط الحالة (State Reset)
```jsx
<EditProfileForm key={selectedUserId} user={user} /> // تغيير المستخدم = إعادة ضبط حالة النموذج بالكامل من الصفر
```

## How to say it in the interview
- "الـ Key هو هوية المكون بالنسبة لـ React. استخدام الفهرس (Index) يربط الهوية بموقع العنصر في المصفوفة لا ببياناته، فعند الإضافة أو الحذف أو الفرز، تظل الحالة وعقد الـ DOM في نفس الموضع بينما تتحرك البيانات بعيداً عنها."
- "استخدام الـ Index مقبول فقط في القوائم الثابتة التي لا يتغير ترتيبها مطلقاً ولا تمتلك عناصرها أي حالة داخلية. وفي غير ذلك، أستخدم دائماً معرّفاً ثابتاً وفريداً مستمداً من البيانات."
- فخ شائع: "React يحذر فقط عند غياب الـ Key بالكامل، لكنه لا يحذر إذا مررت الـ Index"، لذلك يمر الخطأ خلسة دون تنبيه حتى يجرب أحدهم الحذف أو الترتيب.
- الموازنة (Trade-off): تغيير الـ Key عمداً يمثل وسيلة نظيفة جداً لتصفير حالة المكونات (State Reset)، ولكنه يعيد تركيب الشجرة الفرعية بأكملها مما يترتب عليه تكلفة أداء طفيفة.
