# ما هي أساسيات Git التي يحتاجها مطور Frontend للعمل ضمن فريق؟

**المستوى:** مبتدئ (Junior)
**Merged from (original phrasings):**
- كيف تتعامل مع التحكم في الإصدارات والتعاون البرمجي باستخدام Git؟

## The concept (short answer)
- نظام Git هو نظام تحكم في الإصدارات **موزع (distributed)**: يمتلك كل مطور سجل التاريخ كاملاً على جهازه المحلي، ويعمل على **فروع (branches)** مستقلة، ويشارك التغييرات عبر مستودع بعيد (GitHub أو GitLab أو Bitbucket).
- مسار العمل القياسي للفرق (GitHub Flow / trunk-based): يكون الفرع `main` جاهزاً للنشر في بيئة الإنتاج دائماً؛ ولكل مهمة ننشئ **فرع ميزة (feature branch)** قصير العمر، ونكتب تغييرات صغيرة محددة الهدف، ونرفعها، ونفتح **طلب سحب (Pull Request / PR)**، ونحصل على **مراجعة الكود (code review)** ونجاح فحوصات **الـ CI** (التدقيق والاختبارات والبناء)، ثم ندمج الفرع.
- حافظ على تحديث فرعك باستمرار عبر `git fetch` ثم `git rebase origin/main` (أو دمج `main` داخله)، وحل أي تعارضات (conflicts) محلياً قبل طلب المراجعة.
- اكتب رسائل إيداع (commit messages) ذات معنى واضح (باتباع Conventional Commits مثل: `fix(cart): prevent negative quantity`)، مع إيداع تغيير منطقي واحد لكل commit.
- احمِ الفرع `main` بقواعد حماية الفروع (branch protection rules): منع الرفع المباشر، اشتراط المراجعة والموافقة، اشتراط اجتياز فحوصات الـ CI، ومنع الرفع الإجباري (force-push).
- اعرف أدوات الأمان والطوارئ: `git stash` لحفظ التعديلات مؤقتاً، و `git revert` للتراجع الآمن عن commit تم رفعه مسبقاً، و `git reset` (للعمل المحلي غير المرفوع فقط)، و `git reflog` لاستعادة الـ commits "المفقودة"، وملف `.gitignore` لحجب الأسرار ومخرجات البناء.

## Real-life example: the problem
حالة شائعة: فريق صغير يبني لوحة تحكم لتطبيق سحابي كان يرفع التعديلات مباشرة إلى الفرع `main`، الذي ينشر تلقائياً لبيئة الإنتاج. ويوم الجمعة قام مطوران بتعديل نفس الملف. واجه المطور (ب) رفضاً لعملية الرفع، فشغّل الأمر `git push --force`، فمسح كل إيداعات المطور (أ) التي أنجزها في الصباح من المستودع البعيد! ولاحقاً تم رفع commit يحتوي ملف `.env` بمفتاح Stripe السري الحقيقي إلى مستودع عام، وتعطل الموقع في بيئة الإنتاج لأن كوداً غير مختبر انتقل مباشرة من حاسوب محمول إلى العملاء.

```bash
# مسار العمل "الفوضوي" سابقاً
git add .                       # يشمل ملفات .env وتعديلات node_modules دون انتباه
git commit -m "stuff"           # رسالة مبهمة عديمة الفائدة، مع تعديل 40 ملفاً دفعة واحدة
git push origin main            # رُفضت العملية: المستودع البعيد يحتوي تعديلات أحدث
git push --force origin main    # مسح عمل الزميل من المستودع البعيد تماماً!
```

## How to fix it
```bash
# 1. ابدأ دائماً من نسخة محدثة من main، وأنشئ فرعاً يحمل اسم المهمة
git switch main
git pull --ff-only
git switch -c feature/DASH-142-export-csv

# 2. إيداعات صغيرة ومحددة؛ راجع بدقة ما تقوم بتجهيزه
git add -p                                   # تجهيز التغييرات تفاعلياً كتلة بكتلة في الطرفية
git commit -m "feat(reports): add CSV export button"

# 3. مزامنة الفرع مع main قبل فتح الـ PR
git fetch origin
git rebase origin/main                       # حل أي تعارضات محلياً، ثم: git rebase --continue
git push -u origin feature/DASH-142-export-csv
# إذا قمت بعمل rebase لفرع رفعته مسبقاً (فرعك الخاص فقط):
git push --force-with-lease                  # ترفض العملية إذا رفع شخص آخر تعديلات أثناء ذلك

# 4. فتح PR -> مراجعة وقبول -> نجاح الـ CI -> دمج عبر squash & merge -> حذف الفرع
```

```yaml
# .github/workflows/ci.yml: يعمل مع كل PR ومفروض عبر حماية الفرع
name: CI
on:
  pull_request:
    branches: [main]
jobs:
  checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run lint
      - run: npm test -- --ci
      - run: npm run build
```

بالإضافة إلى تفعيل حماية `main` في إعدادات GitHub: اشتراط فتح PR، موافقة واحدة على الأقل، اجتياز فحوصات الـ CI، وحظر الـ force-push تماماً.

لماذا ينجح هذا الحل:
- تضمن فروع الميزات وطلبات السحب عدم مساس أي شخص بـ `main` مباشرة؛ وتكتشف المراجعات والـ CI الأخطاء قبل وصولها للإنتاج.
- يمنع خيار `--force-with-lease` الكتابة فوق عمل الزملاء بالخطأ، بينما تحظر حماية الفروع الرفع الإجباري على `main` كلياً.
- يمنع ملف `.gitignore` وصول الأسرار ومخرجات البناء إلى السجل. وإذا تم رفع مفتاح سري بالخطأ، **فيجب تدويره وتغييره فوراً**، فحذف الملف لا يزيله من سجل Git القديم.
- تجعل الإيداعات الصغيرة الواضحة عمليات المراجعة، وتتبع التغييرات بـ `git blame`، واكتشاف الأخطاء بـ `git bisect`، والتراجع بـ `git revert` أمراً غاية في السهولة.

التراجع عن الأخطاء: تراجع عن أي دمج خاطئ في `main` باستخدام `git revert <sha>` (ينشئ commit جديداً ويحفظ السجل)؛ واسترجع أي عمل محلي مفقود باستخدام `git reflog`.

## How to say it in the interview
- "أعتمد مسار عمل فروع الميزات (Feature-branch workflow): فروع قصيرة العمر متفرعة من `main`، وإيداعات صغيرة برسائل واضحة، وفتح PR مع المراجعة وفحوصات الـ CI، ثم الدمج بـ squash-merge. ويبقى الفرع `main` محمياً وجاهزاً للنشر دائماً."
- اشرح الفرق بين merge و rebase: تحافظ merge على التاريخ كما حدث بالضبط (مع إنشاء merge commit)؛ بينما تعيد rebase كتابة تاريخ فرعك فوق قمة `main` للحصول على سجل خطي مستقيم. ولا تقم بعمل rebase لفروع عامة مشتركة أبداً.
- فخ المقابلة: "كيف تتراجع عن commit تم رفعه للمستودع المشترك؟" باستخدام `git revert` وليس `git reset --hard` مع force push، لأن زملاءك قد يكونون سحبوا هذا الـ commit بالفعل.
- المفاضلة: تسبب الفروع طويلة العمر تعارضات دمج معقدة ومؤلمة؛ لذا يُفضل فتح طلبات سحب صغيرة مدمجة بانتظام، مع استخدام أعلام الميزات (feature flags) للمهام التي لم تكتمل بعد.
