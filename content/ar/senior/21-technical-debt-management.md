# إدارة الديون التقنية (Technical Debt) في المشاريع الضخمة

**Level:** Senior
**Merged from (original phrasings):**
- ما هو أسلوبك في إدارة الديون التقنية (Technical Debt) في القواعد البرمجية الضخمة؟

## The concept (short answer)

- الديون التقنية هي التكلفة الإضافية التي تدفعها التعديلات المستقبلية بسبب قرارات متسرعة سابقة أو معمارية متقادمة. بعض الديون قد تكون مقبولة ومبررة تجارياً (للإطلاق قبل موعد نهائي حرج)؛ ولكن المشكلة الحقيقية تكمن في **الديون الخفية غير المدارة** التي تتراكم فوائدها دون وعي.
- **اجعل الديون مرئية بالأدلة والأرقام:** إنشاء **سجل للديون التقنية (Debt Register)** (تذاكر موسومة بـ `tech-debt` أو جدول مبسط) يوثق المشكلة، ومكانها، وسبب ضررها، وتكلفة تأجيل حلها (Cost of Delay)، وحجم العمل التقديري لعلاجها. ادعم السجل بمقاييس دقيقة: زمن البناء، ونسبة الاختبارات غير المستقرة (Flaky Tests)، وعدد الأخطاء لكل موديول، ومعدل دوران الكود (Churn) مقابل التعقيد.
- **اربط الدين بأثر الأعمال الملموس:** عبارة مثل "تعديلات صفحة الدفع أصبحت تستغرق 3 أضعاف الوقت المعتاد وتسببت في 4 حوادث تعطل هذا الربع" تحظى بالأولوية والموافقة فوراً؛ بينما عبارة "الكود بشع ويحتاج تحسين" تُرفض وتُهمل.
- **خصص ميزانية ثابتة ومستمرة:** خصص ~15-20% من سعة كل Sprint لسداد الديون التقنية، بالإضافة لمشاريع مخصصة دورية للبنود الكبيرة، بدلاً من انتظار "ربع سنوي لإعادة كتابة الكود" لن يأتي أبداً.
- **قاعدة الكشافة (Boy-scout rule):** اترك أي جزء تلمسه من الكود بحال أفضل مما وجدته (إضافة أنواع Types، اختبارات، استخراج دوال) كجزء أصيل وطبيعي من مهام الميزات اليومية.
- **أوقف تسرب الديون الجديدة عند الباب (Ratcheting):** فرض قواعد فحص (lint) وصارمة الأنواع وفحوصات CI تمنع تسرب أي نماذج سيئة جديدة بينما يتم استهلاك النماذج القديمة تدريجياً.

## Real-life example: the problem

تطبيق SaaS قديم بـ React عمره 5 سنوات. في كل دورة Sprint، تفشل كافة التقديرات الزمنية لقسم "التقارير"؛ وتطلب تعديل فلتر بسيط أسبوعين كاملين وتسبب في انتكاسة أمنية. يحتوي الكود على خليط عشوائي من Class Components، ومخزن Redux قديم، ومكتبة `moment.js`، وكلمة `any` في كل سطر تقريباً، بالإضافة إلى 300 تعليق `// TODO: refactor`. ظل المطورون يطالبون بـ "إعادة كتابة شاملة" طوال عام كامل؛ وقوبلوا بالرفض الدائم من إدارة المنتج لغياب أي تبرير مالي واضح. وفي الوقت نفسه، استمر الكود الجديد في استيراد `moment` وكتابة `any` لأنه لم يكن هناك ما يمنعهم!

```tsx
// reports/ReportFilters.tsx - BROKEN: debt is invisible and keeps growing
// TODO: refactor this mess
// TODO: remove moment
// FIXME: why does this need setTimeout??
import moment from 'moment';

export function ReportFilters(props: any) {
  const range = props.range as any;
  setTimeout(() => props.onChange(moment(range.from).format('YYYY-MM-DD')), 0);
  // ...
}
```

## How to fix it

**1. سجل ديون تقنية مدعوم بالأثر على الأعمال**
```markdown
| ID  | المنطقة  | المشكلة                                   | الأثر والأدلة الميدانية                              | الحجم | الأولوية |
|-----|----------|------------------------------------------|-----------------------------------------------------|------|----------|
| D-1 | التقارير  | فلاتر بلا أنواع، وRedux قديم + setTimeout | 4 انتكاسات في Q3؛ وتعديل الفلتر يستغرق 8 أيام بدلاً من يومين | M    | عالية    |
| D-2 | عام      | مكتبة moment.js (72 KB مضغوطة) في الحزمة | +0.4 ثانية على LCP في الهواتف (مقاسة بـ RUM)        | M    | متوسطة   |
| D-3 | الـ CI   | 9% اختبارات E2E غير مستقرة flaky         | ~6 ساعات عمل مهندسين أسبوعياً لإعادة تشغيل المسارات   | S    | عالية    |
```
تتم مراجعة السجل شهرياً مع مدير المنتج؛ وتُجدول البنود الأعلى أولوية ضمن ميزانية الـ 20% المستمرة.

**2. إغلاق الباب أمام الديون الجديدة وسداد القديم (Ratchet)**

```json

```
تتيح ميزة الـ Bulk Suppressions في ESLint تسجيل عدد الانتهاكات الحالية وإفشال البناء إذا ارتفع العدد مجدداً.

**3. تحسينات الكشافة أثناء تطوير الميزات**
```tsx
// reports/ReportFilters.tsx - after touching it for a feature
import { format } from 'date-fns';

type DateRange = { from: Date; to: Date };
type Props = { range: DateRange; onChange: (from: string) => void };

export function ReportFilters({ range, onChange }: Props) {
  function apply() {
    onChange(format(range.from, 'yyyy-MM-dd'));    // event-driven, no setTimeout hack
  }
  // ...
}
```
مع كتابة اختبار فوري لمنع الانتكاسة التي تم إصلاحها، وربط الـ PR برمز `D-1`.

لماذا ينجح هذا الحل: يُحول السجل الشكاوى الفضفاضة إلى بنود تجارية واضحة مدعومة بالأرقام؛ وتضمن ميزانية الـ 15-20% سداد الفوائد المستمر دون تعطيل إطلاق المنتجات؛ وتمنع قواعد الفحص النزيف البرمجي الجديد؛ وتحدث تحسينات الكشافة في الأماكن التي يعمل فيها المطورون بالفعل وهي الأكثر تكلفة.

## How to say it in the interview

- "أتعامل مع الديون التقنية كمهام عمل ذات مبرر تجاري واضح (Business Case): مسجلة في سجل مرئي، ومقاسة بأرقام مثل سرعة التطوير، وتكرار الحوادث، وحجم الحزمة، وتُناقش مع مسؤولي المنتج."
- "أخصص ميزانية ثابتة تبلغ نحو 15-20% في كل دورة، وأطبق قاعدة الكشافة في مهام الميزات، وأضيف قواعد فحص لمنع تسرب نفس الدين مجدداً."
- فخ المقابلة: "متى تقرر إعادة كتابة المشروع بالكامل (Rewrite)؟" - لا ألجأ تقريباً أبداً لإعادة الكتابة الشاملة المفاجئة (Big Bang)؛ بل أُفضل الاستبدال التدريجي (نمط خناق التين Strangler Fig) مع مراحل تسليم واضحة ومقاسة.
- المفاضلة (Trade-off): ليست كل الديون مستحقة للسداد؛ فالأكواد نادرة التغيير والتي لا تتعطل يمكن أن تظل كما هي. ركّز جهدك على النقاط الساخنة (Hotspots) التي يلتقي فيها تكرار التعديل مع حجم المعاناة البرمجية.
