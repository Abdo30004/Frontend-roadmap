# بناء Design System يتوسع عبر فرق متعددة (Scales Across Teams)

**Level:** Senior
**Merged from (original phrasings):**
- كيف تُنفذ نظام تصميم (Design System) يتوسع بنجاح عبر فرق عمل متعددة؟

## The concept (short answer)

- نظام التصميم (Design System) هو **منتج مستقل بذاته** وليس مجرد مجلد يحتوي على مكونات: فهو يجمع متغيرات التصميم (Design Tokens) + مكتبة المكونات + التوثيق + آلية الحوكمة (Governance)، مع وجود فريق مسؤول ومستهلكين لهذا المنتج.
- **متغيرات التصميم (Design Tokens):** (الألوان، والمسافات، والطباعة، وأنصاف الأقطار، والحركة) هي المصدر الوحيد للحقيقة، وتُخزن كبيانات (JSON / بصيغة رموز W3C) وتُترجم آلياً إلى متغيرات CSS وثوابت TypeScript وصيغ مخصصة للتطبيقات الأصلية (عبر Style Dictionary). تستهلك المكونات متغيرات دلالية (Semantic Tokens مثل `--color-action-primary`)، وتتجنب تماماً استخدام قيم الألوان السداسية الخام (raw hex)، مما يجعل تغيير المظهر والوضع الداكن مجرد تبديل لقيم المتغيرات.
- يُطرح كنظام **حزم ذات إصدارات محددة (Versioned Package)** (وفق معايير semver و changesets وسجل التغييرات changelog) حتى ترقي الفرق إصداراتها بمرونة وبمعرفة واضحة بالتغييرات الجذرية.
- تُعد أداة **Storybook** بمثابة التوثيق وورشة العمل: يُعرض كل سيناريو وحالة لكل مكون كقصة (Story)، مع جداول الخصائص، وإرشادات الاستخدام، وفحوصات الإتاحة وسهولة الوصول الرقمي (عبر إضافة addon-a11y).
- **اختبارات الانحدار البصري (Visual Regression Testing):** (باستخدام Chromatic أو لقطات Playwright أو Loki) في كل طلب PR لكشف أي تغيرات غير مقصودة في البيكسلات عبر كافة القصص.
- **الحوكمة (Governance):** نموذج مساهمة مرن (طلبات RFC للمكونات الجديدة، ومساهمات "المصدر الداخلي InnerSource" من فرق المنتجات، مع مراجعة الفريق الأساسي)، و**أكواد التحويل الآلي (Codemods)** (باستخدام jscodeshift أو ts-morph) للتغييرات الجذرية لتسهيل ترقية الإصدارات دون عناء يدوي.

## Real-life example: the problem

شركة تضم 5 فرق منتجات لديها مجلد `ui` مشترك يتم نسخه ولصقه يدوياً بين المستودعات. قررت الشركة تغيير الهوية واستبدال درجة اللون الأزرق الأساسي. وبعد ثلاثة أشهر، كانت النتيجة: موقع التسويق، ولوحة التحكم، وصفحة الدفع تعرض ثلاث درجات زرقاء متباينة، وارتفاعين مختلفين للأزرار، ونافذة منبثقة (modal) غير قابلة للاستخدام عبر لوحة المفاتيح في أحد التطبيقات. وتسبب تعديل "بسيط" في مكون `Button` (إعادة تسمية `type="primary"` إلى `variant="primary"`) دُمج مباشرة في الفرع الرئيسي في تعطل صامت لصفحة الدفع، حيث ارتدت الأزرار إلى نمط رمادي افتراضي دون تنسيق.

```tsx
// Button.tsx - BROKEN: hard-coded values, unversioned, silent API break
export function Button({ variant, children, ...rest }: Props) {
  const bg = variant === 'primary' ? '#1a73e8' : '#eeeeee';   // raw hex, copied around
  return (
    <button style={{ background: bg, padding: '9px 15px', borderRadius: 3 }} {...rest}>
      {children}
    </button>
  );
}
// old callers still pass type="primary" -> rendered grey, no error, no warning
```

```json
// apps/checkout/package.json - BROKEN: consumes the library from a git branch
{ "dependencies": { "@acme/ui": "github:acme/ui#main" } }
```

## How to fix it

**1. المتغيرات كبيانات، تترجم إلى متغيرات CSS**
```json
// tokens/color.json (W3C design tokens format)
{
  "color": {
    "brand": { "blue-600": { "$value": "#1a5fd0", "$type": "color" } },
    "action": { "primary": { "$value": "{color.brand.blue-600}", "$type": "color" } }
  }
}
```
```css
/* generated by Style Dictionary -> tokens.css */
:root { --color-action-primary: #1a5fd0; --space-2: 8px; --space-4: 16px; --radius-md: 6px; }
[data-theme='dark'] { --color-action-primary: #6f9cf0; }
```

**2. المكونات تعتمد متغيرات دلالية وتحذر بصوت عالٍ من الـ APIs القديمة**
```tsx
import styles from './Button.module.css';

type Props = React.ButtonHTMLAttributes<HTMLButtonElement> & {
  variant?: 'primary' | 'secondary';
  /** @deprecated use `variant`. Removed in v4. */
  kind?: 'primary' | 'secondary';
};

export function Button({ variant, kind, className, ...rest }: Props) {
  if (kind && process.env.NODE_ENV !== 'production') {
    console.warn('[ui] Button `kind` is deprecated, use `variant`. Run: npx @acme/ui-codemods button-variant');
  }
  const v = variant ?? kind ?? 'secondary';
  return <button className={`${styles.button} ${styles[v]} ${className ?? ''}`} {...rest} />;
}
```
```css
/* Button.module.css */
.button { padding: var(--space-2) var(--space-4); border-radius: var(--radius-md); }
.primary { background: var(--color-action-primary); color: var(--color-text-on-action); }
```

**3. إطلاق سكربت تحويل آلي Codemod مع الإصدار الرئيسي الجديد**
```js
// codemods/button-variant.js (jscodeshift)
export default function transform(file, api) {
  const j = api.jscodeshift;
  return j(file.source)
    .findJSXElements('Button')
    .find(j.JSXAttribute, { name: { name: 'kind' } })
    .forEach((p) => { p.node.name.name = 'variant'; })
    .toSource();
}
```

**4. مسار النشر المؤتمت والحوكمة**
```yaml
# .github/workflows/ui.yml (excerpt)
- run: pnpm build-storybook
- run: npx chromatic --exit-zero-on-changes=false   # visual diff must be approved
- run: pnpm changeset version && pnpm publish -r     # semver release with changelog
```
تعتمد التطبيقات المستهلكة على حزمة محددة `"@acme/ui": "^3.4.0"`، وتتولى أدوات الترقية الآلية (Renovate) فتح طلبات التحديث. وتمر المكونات الجديدة عبر مقترح RFC موجز؛ ويمكن لأي فريق المساهمة، بينما يُراجع الفريق الأساسي اتساق الواجهات والإتاحة والالتزام بالرموز. كما تمنع قواعد ESLint كتابة قيم ألوان ثابتة في أكواد التطبيقات.

لماذا ينجح هذا الحل: تغيير متغير تصميم واحد يُعيد تلوين كافة التطبيقات فوراً وبشكل متناسق؛ وتحول حزم semver مع سجل التغييرات والـ codemods التغييرات الكبرى إلى ترقية سهلة تستغرق 10 دقائق بدلاً من أعطال غامضة؛ وتكشف اختبارات الانحدار البصري أي فوارق دقيقة في البيكسلات تفوت على العين البشرية.

## How to say it in the interview

- "المتغيرات (Tokens) هي حجر الأساس، والمكونات تُبنى حصرياً على متغيرات دلالية، وتُنشر المكتبة كحزمة semver محددة الإصدارات مع توثيق Storybook واختبارات انحدار بصري مؤتمتة."
- "تبني نظام التصميم تحدٍ إنساني وتنظيمي: نموذج مساهمة واضح وساعات عمل مفتوحة للدعم، مع جعل التصرف الصحيح هو الأسهل عبر قواعد الفحص والـ codemods."
- فخ المقابلة: "كيف تقيس نسبة تبني النظام (Adoption rate)؟" - فحص مستودعات المشاريع لحساب نسبة استيراد `@acme/ui` مقابل المكونات المحلية والألوان الثابتة، وتتبع توزيع الإصدارات عبر التطبيقات.
- المفاضلة (Trade-off): صرامة النظام المفرطة تدفع الفرق إلى نسخه وتعديله جانباً (fork). وفر منافذ مرونة مدروسة (`className`، والتركيب composition، واستخدام أصول عديمة التنسيق headless primitives كـ Radix) مع الإبقاء على إلزامية متغيرات التصميم.
