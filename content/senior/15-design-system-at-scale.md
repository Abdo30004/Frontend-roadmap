# Implementing a Design System That Scales Across Teams

**Level:** Senior
**Merged from (original phrasings):**
- How do you implement a design system that scales across multiple teams?

## The concept (short answer)
- A design system is a **product**, not a folder of components: design tokens + a component library + documentation + a governance process, with an owning team and consumers.
- **Design tokens** (color, spacing, typography, radius, motion) are the single source of truth, stored as data (JSON / W3C tokens format) and compiled to CSS variables, TS constants and native formats (Style Dictionary). Components consume semantic tokens (`--color-action-primary`), never raw hex values, which makes theming and dark mode a token swap.
- Ship it as a **versioned package** (semver, changesets, changelog) so teams upgrade on their schedule and breaking changes are explicit.
- **Storybook** is the docs and the workshop: every component state as a story, with props tables, usage guidelines and accessibility checks (addon-a11y).
- **Visual regression testing** (Chromatic, Playwright screenshots, Loki) on every PR catches unintended pixel changes across all stories.
- **Governance**: a contribution model (RFC for new components, "inner source" PRs from product teams, review by the core team), and **codemods** (jscodeshift / ts-morph) for breaking API changes so upgrades are cheap.

## Real-life example: the problem
A typical case: a company with five product teams has a shared `ui` folder copied between repos. A rebrand changes the primary blue. Three months later the marketing site, the dashboard and the mobile web checkout show three different blues, two button heights and a modal that is not keyboard-accessible in one app. A "small" change to `Button` (renaming `type="primary"` to `variant="primary"`) is merged directly to main and silently breaks the checkout page, because buttons fall back to an unstyled default.

```tsx
// Button.tsx - BROKEN: hard-coded values, unversioned, silent API break
export function Button({ variant, children, ...rest }: Props) {
  const bg = variant === 'primary' ? '#1a73e8' : '#eeeeee';   // raw hex, copied around
  return (
    <button style={{ background: bg, padding: '9px 15px', borderRadius: 3 }} {...rest}>
      {children}
    </button>
  );
}
// old callers still pass type="primary" -> rendered grey, no error, no warning
```

```json
// apps/checkout/package.json - BROKEN: consumes the library from a git branch
{ "dependencies": { "@acme/ui": "github:acme/ui#main" } }
```

## How to fix it
**1. Tokens as data, compiled to CSS variables**
```json
// tokens/color.json (W3C design tokens format)
{
  "color": {
    "brand": { "blue-600": { "$value": "#1a5fd0", "$type": "color" } },
    "action": { "primary": { "$value": "{color.brand.blue-600}", "$type": "color" } }
  }
}
```
```css
/* generated by Style Dictionary -> tokens.css */
:root { --color-action-primary: #1a5fd0; --space-2: 8px; --space-4: 16px; --radius-md: 6px; }
[data-theme='dark'] { --color-action-primary: #6f9cf0; }
```

**2. Components use semantic tokens and deprecate old APIs loudly**
```tsx
import styles from './Button.module.css';

type Props = React.ButtonHTMLAttributes<HTMLButtonElement> & {
  variant?: 'primary' | 'secondary';
  /** @deprecated use `variant`. Removed in v4. */
  kind?: 'primary' | 'secondary';
};

export function Button({ variant, kind, className, ...rest }: Props) {
  if (kind && process.env.NODE_ENV !== 'production') {
    console.warn('[ui] Button `kind` is deprecated, use `variant`. Run: npx @acme/ui-codemods button-variant');
  }
  const v = variant ?? kind ?? 'secondary';
  return <button className={`${styles.button} ${styles[v]} ${className ?? ''}`} {...rest} />;
}
```
```css
/* Button.module.css */
.button { padding: var(--space-2) var(--space-4); border-radius: var(--radius-md); }
.primary { background: var(--color-action-primary); color: var(--color-text-on-action); }
```

**3. A codemod ships with the major version**
```js
// codemods/button-variant.js (jscodeshift)
export default function transform(file, api) {
  const j = api.jscodeshift;
  return j(file.source)
    .findJSXElements('Button')
    .find(j.JSXAttribute, { name: { name: 'kind' } })
    .forEach((p) => { p.node.name.name = 'variant'; })
    .toSource();
}
```

**4. Pipeline and governance**
```yaml
# .github/workflows/ui.yml (excerpt)
- run: pnpm build-storybook
- run: npx chromatic --exit-zero-on-changes=false   # visual diff must be approved
- run: pnpm changeset version && pnpm publish -r     # semver release with changelog
```
Consumers depend on `"@acme/ui": "^3.4.0"`; Renovate opens upgrade PRs. New components go through a short RFC; product teams can contribute, the core team reviews for API consistency, accessibility and tokens usage. An ESLint rule (`no-restricted-syntax` for hex colors, or `stylelint-declaration-strict-value`) blocks raw values in apps.

Why it works: one token change re-themes every app; semver + changelog + deprecation warnings + codemods turn breaking changes into a 10-minute upgrade instead of a silent bug; visual regression catches the pixel diffs reviewers miss.

## How to say it in the interview
- "Tokens are the foundation, components are built only on semantic tokens, and the library ships as a semver package with Storybook docs and visual regression tests."
- "Adoption is a people problem: a clear contribution model, office hours, and making the right thing the easy thing with lint rules and codemods."
- Follow-up trap: "How do you measure adoption?" Scan repos for imports of `@acme/ui` vs local components and for hard-coded colors; track the version spread across apps.
- Trade-off: a too-rigid system makes teams fork it. Provide escape hatches (`className`, composition/slots, headless primitives like Radix) while keeping tokens mandatory.
